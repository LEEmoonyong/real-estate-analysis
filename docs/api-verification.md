## 카카오 로컬 실측 (2026-11-04)

- REST API 키 + `Authorization: KakaoAK` 헤더로 정상 응답. 웹 플랫폼 도메인 등록 없이 서버 호출 가능.
- 응답 형식이 공식 문서와 일치: `documents[].x/y`는 문자열, 키워드 검색은 `place_name`·`category_name`·`road_address_name` 포함.
- 단지명 검색("잠실엘스", "해운대 마린시티", "세종 한솔동 첫마을")은 주소 검색 결과가 0건이고 키워드 검색으로만 찾아진다 → 병렬 호출 설계가 맞다.
- 키워드 결과에 "잠실엘스아파트 서문"(카테고리 `교통,수송 > 입출구`)처럼 출입구 POI가 섞인다. 아파트 카테고리를 앞에 정렬하는 현재 방식으로 첫 후보는 단지 자체가 된다.

## V-World 실측 (2026-11-04)

처음 입력한 키는 마지막 한 글자가 빠져 `INVALID_KEY`였고, 키를 고친 뒤 모두 정상 동작했다.
서버 측 요청에 `domain=http://localhost:5173`을 넣은 상태에서 인증이 통과했다.

### 2D 데이터 `LT_C_BLDGINFO` (반경 400m BOX)

| 항목 | 결과 |
|---|---|
| GeoJSON 경로 | `response.result.featureCollection.features` ✅ |
| 피처 ID | `id: "LT_C_BLDGINFO.13713120"` 형식, 응답 내 중복 없음 → 건물 ID로 사용 (`vworld:13713120`) |
| 지오메트리 | **전부 `MultiPolygon`**, 좌표 `[경도, 위도]`, 닫힌 링(첫 점 = 끝 점). 여러 조각이나 구멍이 있는 피처는 부산 2건뿐 |
| 속성 | `bld_nm, dong_nm, usability, grnd_flr, ugrnd_flr, archarea, height, vl_rat, bc_rat, totalarea, platarea, useapr_day, strct_cd` — **숫자도 문자열**로 옴(`"18.4"`), 빈 값은 `""` |
| 페이지 | 잠실 1,099건 → `size=1000`으로 2페이지 순회 정상. BOX 약 800m × 800m에서 면적 제한 오류 없음 |
| 건물 수 | 잠실 1,099 / 마린시티 183 / 세종 한솔동 179 |

**높이·층수 누락**

| 지역 | `height` 없음 | `grnd_flr` 없음 | 둘 다 없음 |
|---|---|---|---|
| 잠실 | 535 (49%) | 213 (19%) | 213 |
| 마린시티 | 122 (67%) | 91 (50%) | 91 |
| 세종 | 121 (68%) | 44 (25%) | 44 |

- 층수가 없으면 높이도 항상 없다. 그런 피처는 `usability`가 빈 값이고 `archarea`도 0에 가깝다.
- 실제 외곽선 면적 중앙값은 잠실 23m², 부산 21m²로, 경비실·창고·구조물 같은 부속 건물이 대부분이다. 세종만 중앙값 298m²로 큰 미등록 건물이 섞여 있다.
- → **정규화 규칙 변경 (PLAN.md 6.1 반영)**: 층수·높이가 없으면 외곽선 면적 < 50m²는 1층, 그 이상은 기본 5층을 쓰고 둘 다 "추정값"으로 표시한다. 기존 안(일괄 10층)은 작은 부속 건물의 그림자를 크게 과장한다.

**층고 검증**: `usability=02000`(공동주택) 중 높이·층수가 모두 있는 건물의 `height / grnd_flr` 평균은 잠실 **2.90m**, 세종 3.08m, 부산 3.36m(주상복합 포함). 기본 층고 2.9m가 타당하다.

**`usability` 코드**: 건축물대장 주용도 코드 체계로 보인다(`01000` 단독주택, `02000` 공동주택, `03000`·`04000` 근린생활시설 …). 공동주택 개수가 실제 단지 동 수와 맞는다. 공식 코드표는 확인하지 못했고, 앱에서는 `02000`을 "아파트(공동주택)" 판별에만 쓴다.

**`dong_nm` 형식**: `"101동"`, `"169동"` 같은 숫자 동 외에 `"씨동"`, `"비동"`, `"주동3"`, `"상가동"`, `"부속건축물제1동"`, 단지명(`"마린시티자이"`)이 섞여 있다. 잠실 공동주택 232건 중 85건이 `^\d{1,4}동$` 형식이다. → 이 정규식에 맞을 때만 동 번호를 자동 지정하고, 나머지는 사용자가 지정한다(B1).

### 지오코더·검색 (카카오 키를 뺀 상태에서 대체 경로 확인)

- 지오코더 `ROAD`: "서울 송파구 올림픽로 99" → `(잠실동,잠실엘스)` 정상. 단지명 "잠실엘스"도 `refine=true` 덕분에 도로명 주소로 찾아졌다.
- 검색 API(`type=PLACE`)는 최상위에 `response` 래퍼가 있는 형태로 응답했다(양쪽 형태를 모두 처리하는 코드 유지).
- 장소 검색이 주소 검색어에 느슨하게 걸린다("세종특별자치시 나리로 57" → "경부선", "고북군립공원") → `isRelevantPlace` 필터를 추가했다(검색어 토큰이 이름에 들어간 장소만 남김, 단위 테스트 포함).

## OSM Overpass 실측

반경 400m, `way["building"]` + `relation["building"]["type"="multipolygon"]`, `out tags geom`.

| 미러 | 결과 (2026-11-04 02시경 KST) |
|---|---|
| `overpass-api.de` | 502 / 504 (과부하) |
| `overpass.private.coffee` | 60초 무응답 |
| `maps.mail.ru` | 200, 약 26초 |

- **CORS**: OPTIONS 요청에 `Access-Control-*` 헤더가 오지 않았다 → 프록시 경유 결정 유지.
- **결론**: Overpass는 대체 소스로만 쓰고, 채점·시연용 경로는 반드시 샘플 JSON으로 보장한다. 프록시는 마지막 성공 미러를 먼저 시도한다. 클라이언트에는 "OSM 응답 대기 중(최대 30초)" 안내가 필요하다(4일차 반영).

| 샘플 후보 | 건물 수 | `building=apartments` | 층수 태그 | 동 번호 |
|---|---|---|---|---|
| 서울 잠실 (37.5115, 127.0830) | 625 | 221 | 아파트 69/221 (`building:levels`·`height`) | `name` 태그에 "163", "102" 같은 동 번호가 들어 있음 |
| 부산 마린시티 (35.1567, 129.1450) | 49 | 33 | 49/49 (`height` 35) | "102동" 형태 1건 |
| 세종 한솔동 (36.4795, 127.2560) | — | — | — | 모든 미러 실패, 2일차 재시도 |

→ 잠실은 층수 누락이 많아 샘플에 시연용 층수 보정값이 필요하다(`heightSource`로 구분, README에 명시).

## 태양 위치 기준값 (JPL Horizons)

PLAN.md 9.1의 "NOAA 웹 계산기 기준값"은 **NASA/JPL Horizons API**로 대체했다.
NOAA 식을 독립적으로 검증하려면 다른 방식으로 계산된 기준이 필요하다. Horizons는 DE441 천체력 기반의 고정밀 값을 키 없이 제공한다.

- 요청: `COMMAND='10'`(태양), `CENTER='coord@399'`, `COORD_TYPE='GEODETIC'`, `QUANTITIES='4'`(겉보기 방위각·고도), `APPARENT='AIRLESS'`(굴절 미적용)
- 범위: 서울·부산·제주 × 2026-03-20 / 06-21 / 09-23 / 12-22 × KST 06~18시 정각
- 일출·일몰: 1분 간격 고도에서 기하 고도 −0.833° 교차 시각(NOAA 관례와 같은 정의)
- 결과 파일: `src/test/fixtures/sun-reference.json` (생성: `npx tsx scripts/fetch-sun-reference.ts`)
- 기본 확인: 서울 하지 일출 05:11·일몰 19:56, 동지 07:43·17:17 → 천문연 공표값과 일치
